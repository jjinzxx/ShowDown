## 프로젝트를 통해 확인한 점

### 규칙과 연출을 분리해야 반복 수정이 가능하다

카드·베팅·룰렛 판정과 카메라·사운드·VFX를 분리하면서 코어 로직을 유지한 채 연출을 반복해서 개선할 수 있었습니다. 이벤트 중심 구조는 멀티플레이 동기화 지점을 찾는 데도 도움이 됐습니다.

### 멀티플레이에서는 화면보다 상태의 소유권이 먼저다

로컬 플레이에서 정상인 기능도 서버 권한, 복제 시점과 RPC 방향이 명확하지 않으면 두 화면에서 다르게 보였습니다. 누가 계산하고, 무엇을 복제하며, 어떤 연출을 각 클라이언트에서 실행할지 먼저 정하는 것이 중요했습니다.

### 대용량 에셋은 초기에 관리 기준을 정해야 한다

Unreal 에셋과 음성 모델을 Git LFS로 관리하면서 협업은 가능해졌지만 저장소 크기와 다운로드 시간이 커졌습니다. 필요한 원본, 런타임 의존성, 재생성 가능한 파일을 초기에 분류하는 과정이 필요했습니다.

### 외부 서비스는 실패를 기본 흐름으로 다뤄야 한다

EOS, Supabase와 음성 API는 네트워크나 인증 상태에 따라 실패할 수 있습니다. 성공 흐름뿐 아니라 타임아웃, 재시도, 기본 대사와 사용자 안내까지 기능의 일부로 설계해야 했습니다.

## KPT

### Keep

- 코어 게임 이벤트와 연출 코드의 역할 분리
- 테스트맵에서 기능을 검증한 후 메인 레벨에 통합한 방식
- 멀티플레이 문제를 서버 상태와 로컬 표현으로 나눠 추적한 방식
- 역할별 문서와 설정 로그를 남긴 협업 습관

### Problem

- 같은 레벨과 바이너리 에셋을 여러 명이 수정할 때 병합 비용이 컸습니다.
- 기능 통합이 후반에 집중되면서 네트워크·UI·연출 문제를 동시에 수정해야 했습니다.
- 대용량 에셋과 로컬 AI 모델 때문에 clone과 checkout 비용이 증가했습니다.
- 외부 서비스 오류와 패키징 환경을 더 일찍 검증하지 못했습니다.

### Try

- 주 단위 통합 빌드와 멀티플레이 회귀 테스트를 자동화합니다.
- 메인 레벨 수정 예약과 에셋 소유권 규칙을 더 명확히 운영합니다.
- Unreal Reference Viewer를 이용해 미사용 에셋을 정기적으로 정리합니다.
- 외부 API를 감싼 공통 재시도·오류 UI 계층을 구축합니다.
- 패키징된 두 클라이언트를 이용한 실환경 테스트 시나리오를 체크리스트화합니다.

## 팀원별 회고 작성란

최종 발표 전 각 팀원이 아래 질문에 짧게 답해 회고를 완성합니다.

1. 가장 잘했다고 생각하는 선택은 무엇인가?
2. 가장 오래 걸린 문제와 해결 방법은 무엇인가?
3. 다시 시작한다면 가장 먼저 바꾸고 싶은 것은 무엇인가?
4. 이번 프로젝트에서 새롭게 익힌 기술은 무엇인가?
